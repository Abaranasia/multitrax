## Superseded Fix Record: B.12 (implementation detail, kept for follow-up reference — not part of the shipped diff)

**Source**: An adversarial code-review pass (`review-resilience` lens), independently corroborated by a refuter pass, flagged one CRITICAL finding: a real, reachable race between overlapping `dialog:openAudioFiles` invocations.

**The bug**: `dialog:openAudioFiles` in `src/main/main.ts` correctly REPLACEs (not accumulates) the `grantedPaths` allowlist on every invocation — this semantic is intentional and already covered by its own regression test (B.10); it was NOT touched by this fix. The gap was entirely on the renderer side: `src/renderer/components/Canvas/Canvas.tsx`'s "+ Open Files" button had no disabled/loading state, and `src/renderer/components/Canvas/useCanvas.ts`'s `onOpenFiles` had no in-flight guard and no try/catch around its per-file `readAudioFile` loop. If a user clicked "Open Files" a second time while the first batch's reads were still pending, the second dialog invocation wiped the first batch's allowlist grants mid-flight; the first batch's still-pending `readAudioFile` calls then rejected with "Access denied," the unguarded loop threw before `addTracks(files)` was ever called, and every file already read in that first batch was silently discarded with zero UI feedback (an unhandled promise rejection).

**Fix** (minimal, matches this change's established `console.error`-only/no-new-notification-system convention — no toast system added):
1. `src/renderer/components/Canvas/useCanvas.ts` — added an `isOpeningFilesRef` (a `useRef`, checked synchronously at the top of `onOpenFiles`, ahead of any React re-render) so a second invocation while one is already in flight is an immediate no-op; the existing dialog+read+`addTracks` body is now wrapped in try/finally so the busy flags always clear, even on error. Also added a `useState`-backed `isOpeningFiles` boolean returned from the hook for the UI to consume.
2. `src/renderer/components/Canvas/Canvas.tsx` — disables the "+ Open Files" button (`disabled={isOpeningFiles}`) while a batch is in flight, mirroring `RecorderBar.tsx`'s existing `disabled={isSaving}` convention (the only other async-busy-signaling pattern in the codebase).
3. `onDrop` was read and confirmed unaffected — it uses the browser `File.arrayBuffer()` path and never calls `readAudioFile`, so it shares no code with this fix and needed no change.

## Post-Review-Resilience Fix: B.11 — Silent Save-Failure Data Loss (CRITICAL finding, review-resilience lens)

**Source**: An adversarial code-review pass (`review-resilience` lens — a fresh reviewer lens run against this change, distinct from and after the `sdd-verify` pass already recorded at topic_key `sdd/error-handling-gaps/verify-report`) flagged one CRITICAL finding at `src/main/main.ts:84-89`.

**The bug**: Slice B (B.7) wrapped `fs.writeFileSync` in `dialog:saveRecording` in try/catch, returning `{ saved: false, error }` on failure instead of throwing — correct in isolation. But the only caller, `src/renderer/components/Recorder/useRecorder.ts`'s `recorder.onstop` handler, did `await window.electronAPI.saveRecording(...)` and unconditionally called `setStatus('idle')` right after, never inspecting the returned result. `src/main/preload.ts` and `src/renderer/types/electron.d.ts` typed the return as `Promise<{ saved: boolean; filePath?: string }>` — no `error` field surfaced to typed callers at all. `RecorderBar.tsx` had no error/failure render state — only `'Saving…'` vs `'Record'`.

**Why it's a genuine regression (not pre-existing)**: before Slice B, an uncaught `writeFileSync` throw rejected the IPC promise, so `setStatus('idle')` never ran — the recorder visibly stuck on `'Saving…'` plus an unhandled-rejection console error (bad UX, but observable). After Slice B, the same failure (disk full, EACCES, invalid path) silently resolved to a normal `{ saved: false, error }` value that nobody read; the UI proceeded straight to `'idle'`/`'Record'` as if the save succeeded, and the recorded audio buffer was silently discarded with zero user-visible or logged trace.

**Fix** (minimal, matches this change's established `console.error`-only error-surfacing convention from Slices A/B — no new toast/notification system, per the user's standing decision for this whole change):
1. `src/main/preload.ts` and `src/renderer/types/electron.d.ts` — widened `saveRecording`'s return type to `Promise<{ saved: boolean; filePath?: string; error?: string }>`, matching what `main.ts`'s handler already returns at runtime (no runtime change needed there — `main.test.ts` already asserted the `{ saved: false, error }` shape via B.3/B.10; this was purely a type-contract gap).
2. `src/renderer/components/Recorder/useRecorder.ts` — added a 4th `RecorderStatus` value (`'idle' | 'recording' | 'saving' | 'error'`). In `recorder.onstop`, the IPC result is now inspected: if `!result.saved`, `console.error('Failed to save recording', result.error)` is called and status becomes `'error'` (returning early, skipping the `'idle'` transition); on success, `'idle'` is set as before. The hook now also returns `isError: status === 'error'`.
3. `src/renderer/components/Recorder/RecorderBar.tsx` — added one render branch: `isError ? 'Save failed' : (...)`, so a failed save is visibly distinct from both `'Saving…'` and the plain `'Record'` idle state. No toast/notification system added, per user's standing decision.

## Post-Verify Fix: B.10 — REPLACE-vs-Accumulate Regression Test (CRITICAL finding)

`sdd-verify` (topic_key `sdd/error-handling-gaps/verify-report`) returned **FAIL** with 1 CRITICAL finding: the `grantedPaths` allowlist's REPLACE-per-dialog-call semantics in `src/main/main.ts` (`grantedPaths.clear()` before re-adding paths on every `dialog:openAudioFiles` call) was correct on direct source inspection, but `src/__tests__/main/main.test.ts` had zero test proving REPLACE vs. accumulate — every existing test used the same static `showOpenDialog` mock (`filePaths: ['foo.wav']`), so an accidental future regression (e.g. removing `.clear()`) would pass the whole suite unchanged. This corresponds to spec scenario "A new dialog invocation resets prior grants" (`audio-file-access-security` spec), which was UNTESTED per the verify report's Spec Compliance Matrix.

**Fix**: Added one new test to `src/__tests__/main/main.test.ts`:
- Grants `/path/a.wav` via `dialog:openAudioFiles` (mocked `showOpenDialog.mockResolvedValueOnce`), confirms `fs:readAudioFile` for the resolved path succeeds (`resolves.toEqual(data.buffer)`, matching the file's existing assertion convention rather than `toBeInstanceOf` — see Learned below).
- Invokes `dialog:openAudioFiles` again with a different mocked path (`/path/b.wav`).
- Asserts `fs:readAudioFile('/path/a.wav')` now **rejects** with `Access denied` (proving the first grant was replaced, not retained) AND `fs:readAudioFile('/path/b.wav')` **succeeds** (proving the new grant is active).

**Learned**: The project's vitest config sets `environment: 'jsdom'` (`vitest.config.ts`), so the test file's global `ArrayBuffer` constructor is jsdom's, not Node's. An initial version of this test used `.resolves.toBeInstanceOf(ArrayBuffer)`, which failed even against the correct implementation — the value returned by `fs.readFileSync(...).buffer` is a genuine Node `ArrayBuffer`, but `instanceof` fails across the two separate realms. Switched to `.resolves.toEqual(data.buffer)`, matching the pattern already used by the pre-existing "fs:readAudioFile returns ArrayBuffer..." test in the same file, which sidesteps the realm mismatch via structural equality instead of identity/prototype-chain checks. Anyone adding new `ArrayBuffer`-returning assertions in this codebase's main-process tests should use `toEqual`, not `toBeInstanceOf`, for this reason.
